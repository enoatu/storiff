# storiff

storiff は story(お話)と diff(変更点)を合わせた名前。いま変更したコードを意図ごとに小さなステップに分け、紙芝居のように順番に見せてレビューしてもらう。本体は `~/.claude/skills/storiff/storiff.js`、細かい仕様は `~/.claude/skills/storiff/docs/story-schema.md`

## 用語

| 用語 | 意味 |
| --- | --- |
| ストーリー | レビュー全体。ステップを順に並べた紙芝居 |
| 全体像 | ストーリーの先頭に置く、差分全体の要約と主な変更と気をつける点 |
| ステップ | 紙芝居の1コマ。1つの意図でまとめた変更のかたまり |
| 変更ID | 変更した行1つずつに付く番号。1から順 |
| F番号 | ファイル1個をまるごと指す名前(例 F12) |
| owns | そのステップが受け持つ変更ID。同じ変更IDを2つのステップが持ってはいけない |
| refs | 前に出たコードをもう一度見せるだけ。owns ではない |
| narration | そのステップの説明。何をなぜやったかを書く。fill が後から埋める |
| 区切りの下書き | prep が差分のかたまりから機械で作ったステップの並び。題は仮で説明は空 |
| quiz | そのステップの理解度クイズ。正解するまで画面の「次へ」が止まる。設定で有効にしたときだけ作る |
| diagram | そのステップが触る呼び出し関係だけを描いた小さい図。付けなくてよい |

## 待たせない

ユーザーが最初のコマを読めるまでの時間を、この skill の一番の目安にする。区切りは prep が機械で作り、説明文は fill が後ろで埋める。だから URL は説明文が1つも書けていないうちに渡してよい。

- 説明文が空のコマは、画面に「準備中」と出て、埋まると3秒以内に自分で入れ替わる。左の目次にも準備中と出る
- ステップの題は prep が付けた仮のもので、fill は書き換えない。目次の並びが読んでいる途中でずれないようにするため。仮のまま終わらせず、手順7で意図の言葉に直す
- 待つ仕事(全体像、区切りと題の直し、図、クイズ)はユーザーが読み始めた後ろで進める。URL を渡す前にやらない

## 全体像の書き方

ストーリーの先頭に、差分全体を見渡すための短い文章を1つ置く。ビューアは最初のステップで、これを差分より前に出す。読み手はステップに入る前に、どれくらいの大きさの差分を何のために読むのかをつかめる。

```json
"overview": {
  "summary": "外部から来た id をそのまま db に渡していたので、入口で弾くようにした。あわせて要望のあった削除も入れた",
  "key_changes": ["`getUser` の入口で null を弾く", "`deleteUser` を追加し、使用中のレコードは消さない"],
  "risks": ["削除は元に戻せない。呼び出し側の確認画面はこの差分に入っていない"]
}
```

- summary は数文。何に困っていたかと、どう解いたかを書く。ステップの見出しを並べ直したものにしない
- key_changes は3つから6つくらい。ファイル名の羅列ではなく、読み手が知りたい変更を書く
- risks は、壊れると影響が大きいところ、この差分でやり残したところ、見てほしいところ
- 材料は context.txt と差分にあるものだけを使う。無いことは書かない。危なそうなところが無ければ risks は無理に埋めない
- 任意の項目なので、無くても画面は今まで通り動く。置いたときだけ、空や0件のところを check が参考として知らせる

## 図を付けるステップ

呼び出しの順番や状態のうつり変わりが、差分と説明文だけでは追いにくいステップにだけ図を付ける。全体の構成図は作らない。そのステップが触るものだけを描く。

| 付ける | 付けない |
| --- | --- |
| 処理が別の処理を順に呼ぶ | 名前や文字列の置きかえ |
| 分岐で行き先が変わる | 設定値や依存の更新 |
| 状態が決まった順にうつる | 1つの関数の中で完結する変更 |
| 呼ぶ側と呼ばれる側が別のファイルにある | テストの追加だけ |

書けるのは Mermaid の flowchart の一部だけで、ノードは目安8個まで。check が書き方を検算する。

## 進め方

1. `ts=$(date -u +%Y-%m-%dT%H:%M:%SZ)` で `~/.storiff/$ts/` を作る。これを `<dir>` と呼ぶ
2. `node ~/.claude/skills/storiff/storiff.js prep <dir> --with-draft` で変更点と区切りを書き出す。範囲は引数なしで今の変更。`origin/main...HEAD` のように後ろに付けてもいい。複数リポジトリは `--repo <path> [範囲]` を並べる。changes.json ができなければ「見るものがない」と伝えて終わる
   - `--with-draft` は差分のかたまりから区切りを機械で作って steps.json に置く。ここでステップの分け方を考えない
   - prep は差分と一緒に、意図の材料を `<dir>/context.txt` に集める。手元の git だけで完結し、外には問い合わせない。GitHub の PR や課題も材料にしたいときだけ `--with-remote` を足す。ユーザーが望んでいないなら付けない
3. `node ~/.claude/skills/storiff/storiff.js serve <dir> --session-id "$CLAUDE_CODE_SESSION_ID"` を実行し、返ってきた URL をその場で伝える。ここまで1秒もかからないので、ユーザーはこの時点で開いて読み始められる。serve は tool のタイムアウトに縛られない常駐デーモンを立てて URL をすぐ返すので、裏で動かし続けなくてよい。同じ dir でもう一度実行すると起動済みのビューアにつなぎ直す。画面の「レビュー完了」で done.flag、「終了」で close.flag ができる
   - `--session-id` を渡すと、画面に書かれたコメントに haiku がその場で返事する。haiku はこの会話の履歴を読むだけで、履歴に書き戻さない。この会話の返事を待たずに答えが出るので必ず渡す
4. `node ~/.claude/skills/storiff/storiff.js fill <dir>` を Bash の run_in_background で走らせる。説明文が先頭のコマから順に埋まり、ビューアが3秒ごとに拾って描き直す。終わるのを待たない
5. 全体像をサブエージェントに書かせる。差分全体を見ないと書けない仕事なので、メイン(この会話)にコードを読み込ませない。fill と同時に走らせてよい。prompt は下の「サブエージェントに渡す prompt」。差分の全部に目を通すのはここだけなので、読んでいて気になった漏れや矛盾も一緒に持ち帰らせる。返ってきたら、その気づきを会話でユーザーに伝える。おかしいと思ったことを黙って流さないのがこの skill の役目なので、気づきが無かったときも無かったと伝える
6. Bash を1回だけ裏で動かし、下のループで合図を待つ。ターンを繰り返して待たない

   ```
   until [ -f <dir>/done.flag ] || [ -f <dir>/close.flag ]; do sleep 5; done
   ```

7. 手順4の fill が終わったら、コマの区切りと題を意図の言葉に直す。ユーザーが読んでいる後ろの仕事なので急がない。prep の区切りは git のかたまりをそのまま使っただけで、意図では分かれていない。`<dir>/changes.txt` と埋まった説明文を読み、下の2つを直す
   - 区切り。同じ意図でやったことが離れたコマに散っていればまとめ、1つのコマに別の意図が混ざっていれば分ける。書き換えるのは `owns` の中身だけで、コマを増やしても減らしてもよい
   - 題。仮の題はコードの見出しかファイル名なので、そのままだと目次が `function getUser(id) {` のような羅列になって紙芝居にならない。何をなぜやったかが伝わる短い言葉に直す。題だけを直すときは `owns` も並び順も動かないので、目次の並びはずれない

   `owns` を書き換えると、変更IDがどこにも入らなくなったり2つのコマに入ったりしやすい。直したら手順9の check で必ず確かめる
8. 図とクイズは要るものだけ足す。図は差分と説明文だけでは追いにくいコマにだけ。クイズは手順2の prep が「理解度クイズ: 有効」と出したときだけ。どちらも steps.json のそのコマだけを書き換え、ほかのコマの説明文には触らない
9. 手順7と手順8が済んだら `node ~/.claude/skills/storiff/storiff.js check <dir>` を1回実行する。図もクイズも足さなかったときも必ず実行する。全部の変更IDがちょうど1回ずつどれかのコマに入っていること、つまりストーリーを合わせると指定した差分になることを確かめられるのは check だけ。ng が出たら直してもう一度実行し、ok になってから手順6に戻る
10. close.flag なら片付けて終わり。done.flag なら `<dir>/comments.json` を読み、haiku の返事で足りないコメントに答える。会話で答えつつ `node ~/.claude/skills/storiff/storiff.js reply <dir> <番号> "<本文>"` でも書く(番号は上から1・2…)。あわせて、直しが必要なやり取りだけを短くまとめて自分の理解に入れ、そのまま直す。ストーリーは作り直さない。答えたら `rm <dir>/done.flag` して 6 に戻り、close.flag まで繰り返す
11. 手順10でコードを直したら `node ~/.claude/skills/storiff/storiff.js prep <dir>` をもう一度実行する。追従なので `--with-draft` は付けない。直した差分は末尾の「修正N回目」ステップにまとまるので、そのステップの narration だけ、何をなぜ直したかを書いて `<dir>/steps.json` に足す。ほかのステップは触らない。prep が「理解度クイズ: 有効」と出したときは quiz も1問つける。書いたら `node ~/.claude/skills/storiff/storiff.js check <dir>` を実行する。修正が大きいと「修正N回目」ステップが ng になるので、その場合はステップを割ってから ok になったことを確かめる。書いたら 6 に戻る

## 理解度クイズの作り方

クイズは既定では作らない。`~/.storiff/config.json` に `{"quiz": true}` があるときだけ作る。有効なら prep が「理解度クイズ: 有効」と1行出すので、それを見て判断する。

有効なときは、ステップごとに quiz を1問つける。読み飛ばしを止める関門になり、他人に説明できるところまで理解が届いたかを本人が確かめられる。

```json
"quiz": {
  "question": "この差分の後、`getUser(null)` を呼ぶと何が起きますか",
  "choices": ["例外が投げられる", "null がそのまま返る", "db.find が null で呼ばれる", "空のオブジェクトが返る"],
  "answer": 1,
  "explanation": "先頭に null を弾く分岐を足したので、db に届く前に例外になります"
}
```

- choices は4つくらい。answer は正解の番号で1始まり。explanation は1文か2文
- 差分の中身をたどらないと答えられない問いにする。ここが一番大事
- まちがいの選択肢ももっともらしくする。明らかに変な選択肢を混ぜると当てずっぽうで通ってしまう

良い問い

| 問い | なぜ良いか |
| --- | --- |
| この変更を入れる前は、`id` が null のとき何が起きていましたか | 変更前と変更後を見比べないと答えられない |
| このステップで足した早い return を消すと、どの処理が壊れますか | 差分の周りのコードまで読まないと分からない |
| 同じことは `map` でも書けるのに `forEach` にしたのはなぜですか | 書き方を選んだ理由まで考えさせる |

悪い問い

| 問い | なぜ悪いか |
| --- | --- |
| このステップでは何をしましたか | narration をそのまま読めば答えられる |
| 追加された関数の名前はどれですか | 差分を眺めて探すだけで、理解が要らない |
| 変更した行は何行ですか | 数えるだけで、中身と関わりがない |

quiz は任意なので、無くても画面は今まで通り動く。作りがおかしいときは check が ng にして理由を出す

## サブエージェントに渡す prompt

手順5では、下の文を本物の内容に置きかえて Agent tool(subagent_type: general-purpose)で呼び出す。`<dir>` は本物のパスにする。「作業メモ」は、この会話で実装していたなら要点を書き、していなければ行ごと消す

> `<dir>/steps.json` に、ストーリー全体の題(`title`)と全体像(`overview`)を書いてください。同じ steps.json に別の処理が説明文を書き足している最中なので、`steps` の中身には触らず、Edit で `title` と `overview` の2か所だけを差し替えてください。
>
> - `<dir>/context.txt`(意図の材料)を読む。ブランチ名、その差分に入っているコミットの本文、課題番号、`--with-remote` を付けたときは PR の説明とコメントが入っている。中身が薄いことも空のこともある
> - `<dir>/files.txt`(ファイル一覧)で全体の大きさをつかみ、要ると思ったところだけ `<dir>/changes.txt`(変えた行だけ)で確かめる。changes.json は開かない
> - overview は `summary`(差分全体の要約)と `key_changes`(主な変更の箇条書き)と `risks`(気をつける点の箇条書き)。書き方は `~/.claude/skills/storiff/docs/story-schema.md` の「全体像」に従う
> - 何に困っていて、どう解いたかを書く。ステップの見出しを並べ直したものにしない
> - context.txt にもコードにも無いことは書かない。根拠があるときは「コミットに〜と書いてある」のように出どころを添える。危なそうなところが無ければ risks は無理に埋めない
> - title は差分全体を1行で言い表したもの。ファイル名やステップ数を並べない
> - 書いたら `node ~/.claude/skills/storiff/storiff.js check <dir>` を実行し、全体像について参考の指摘が出ないことを確かめる
> - 作業メモ(どんな順番で何のために作ったか): <この会話で実装した内容の要点。なければこの行を消す>
> - 終わったら title と summary を返す。読んでいて気になった漏れや矛盾、直し残しに見えたところがあれば、どのファイルのどこを見てそう思ったかを添えて一緒に返す。無ければ無いと書く
