# storiff

storiff は story(お話)と diff(変更点)を合わせた名前。いま変更したコードを意図ごとに小さなステップに分け、紙芝居のように順番に見せてレビューしてもらう。本体は `${CLAUDE_PLUGIN_ROOT}/storiff.js`、細かい仕様は `${CLAUDE_PLUGIN_ROOT}/docs/story-schema.md`

## 用語

| 用語 | 意味 |
| --- | --- |
| ストーリー | レビュー全体。ステップを順に並べた紙芝居 |
| 全体像 | ストーリーの先頭に置く、差分全体の要約と主な変更と気をつける点 |
| ステップ | 紙芝居の1コマ。1つの意図でまとめた変更のかたまり |
| 変更ID | 変更した行1つずつに付く番号。1から順 |
| F番号 | ファイル1個をまるごと指す名前(例 F12) |
| owns | そのステップが受け持つ変更ID。同じ変更IDを2つのステップが持ってはいけない |
| refs | 前に出たコードをもう一度見せるだけ。owns ではない |
| narration | そのステップの説明。何をなぜやったかを書く |
| quiz | そのステップの理解度クイズ。正解するまで画面の「次へ」が止まる。設定で有効にしたときだけ作る |
| diagram | そのステップが触る呼び出し関係だけを描いた小さい図。付けなくてよい |

## 全体像の書き方

ストーリーの先頭に、差分全体を見渡すための短い文章を1つ置く。ビューアは最初のステップで、これを差分より前に出す。読み手はステップに入る前に、どれくらいの大きさの差分を何のために読むのかをつかめる。

```json
"overview": {
  "summary": "外部から来た id をそのまま db に渡していたので、入口で弾くようにした。あわせて要望のあった削除も入れた",
  "key_changes": ["`getUser` の入口で null を弾く", "`deleteUser` を追加し、使用中のレコードは消さない"],
  "risks": ["削除は元に戻せない。呼び出し側の確認画面はこの差分に入っていない"]
}
```

- summary は数文。何に困っていたかと、どう解いたかを書く。ステップの見出しを並べ直したものにしない
- key_changes は3つから6つくらい。ファイル名の羅列ではなく、読み手が知りたい変更を書く
- risks は、壊れると影響が大きいところ、この差分でやり残したところ、見てほしいところ
- 材料は context.txt と差分にあるものだけを使う。無いことは書かない。危なそうなところが無ければ risks は無理に埋めない
- 任意の項目なので、無くても画面は今まで通り動く。置いたときだけ、空や0件のところを check が参考として知らせる

## 図を付けるステップ

呼び出しの順番や状態のうつり変わりが、差分と説明文だけでは追いにくいステップにだけ図を付ける。全体の構成図は作らない。そのステップが触るものだけを描く。

| 付ける | 付けない |
| --- | --- |
| 処理が別の処理を順に呼ぶ | 名前や文字列の置きかえ |
| 分岐で行き先が変わる | 設定値や依存の更新 |
| 状態が決まった順にうつる | 1つの関数の中で完結する変更 |
| 呼ぶ側と呼ばれる側が別のファイルにある | テストの追加だけ |

書けるのは Mermaid の flowchart の一部だけで、ノードは目安8個まで。check が書き方を検算する。

## 進め方

1. `ts=$(date -u +%Y-%m-%dT%H:%M:%SZ)` で `~/.storiff/$ts/` を作る。これを `<dir>` と呼ぶ
2. `node ${CLAUDE_PLUGIN_ROOT}/storiff.js prep <dir>` で変更点を書き出す。引数なしで今の変更。`origin/main...HEAD` のように範囲を後ろに付けてもいい。複数リポジトリは `--repo <path> [範囲]` を並べる。changes.json ができなければ「見るものがない」と伝えて終わる
   - prep は差分と一緒に、意図の材料を `<dir>/context.txt` に集める。手元の git だけで完結し、外には問い合わせない。GitHub の PR や課題も材料にしたいときだけ `--with-remote` を足す。ユーザーが望んでいないなら付けない
3. ストーリーはサブエージェントに作らせる。メイン(この会話)に大量のコードを読み込ませないため、steps.json を作るところまでサブエージェント側で終わらせる
   - この会話で実装したなら、メインが「どんな順番で何のために作ったか」を短くまとめ、下の prompt に書いて渡す。サブエージェントはこの会話を見られない
   - まだ実装していない変更なら、まとめは渡さず context.txt と files.txt と changes.txt と hints.txt から組み立てさせる
   - 手順2の prep が「理解度クイズ: 有効」と出したときだけ、下の prompt の quiz の行を残す。出ていなければその行を消し、クイズは作らせない
   - Agent tool(subagent_type: general-purpose)で呼ぶ。メインはステップの数と check の結果だけ受け取り、コードの中身は読まない
4. `node ${CLAUDE_PLUGIN_ROOT}/storiff.js serve <dir> --session-id "$CLAUDE_CODE_SESSION_ID"` を実行し、返ってきた URL を伝える。serve は tool のタイムアウトに縛られない常駐デーモンを立てて URL をすぐ返すので、裏で動かし続けなくてよい。同じ dir でもう一度実行すると起動済みのビューアにつなぎ直す。画面の「レビュー完了」で done.flag、「終了」で close.flag ができる
   - `--session-id` を渡すと、画面に書かれたコメントに haiku がその場で返事する。haiku はこの会話の履歴を読むだけで、履歴に書き戻さない。この会話の返事を待たずに答えが出るので必ず渡す
5. Bash を1回だけ裏で動かし、下のループで合図を待つ。ターンを繰り返して待たない

   ```
   until [ -f <dir>/done.flag ] || [ -f <dir>/close.flag ]; do sleep 5; done
   ```

6. close.flag なら片付けて終わり。done.flag なら `<dir>/comments.json` を読み、haiku の返事で足りないコメントに答える。会話で答えつつ `node ${CLAUDE_PLUGIN_ROOT}/storiff.js reply <dir> <番号> "<本文>"` でも書く(番号は上から1・2…)。あわせて、直しが必要なやり取りだけを短くまとめて自分の理解に入れ、そのまま直す。ストーリーは作り直さない。答えたら `rm <dir>/done.flag` して 5 に戻り、close.flag まで繰り返す
7. 手順6でコードを直したら `node ${CLAUDE_PLUGIN_ROOT}/storiff.js prep <dir>` をもう一度実行する。changes.json と steps.json がすでにあるので追従に切り替わり、直した差分は末尾の「修正N回目」ステップにまとまる。steps.json を作り直させたりはせず、追加された修正ステップの narration だけ、何をなぜ直したかを書いて `<dir>/steps.json` に足す。prep が「理解度クイズ: 有効」と出したときは quiz も1問つける。ほかのステップの quiz はそのまま残る。書いたら `node ${CLAUDE_PLUGIN_ROOT}/storiff.js check <dir>` を実行する。修正が大きいと「修正N回目」ステップが ng になるので、その場合はステップを割ってから ok になったことを確かめる。書いたら 5 に戻る

## 理解度クイズの作り方

クイズは既定では作らない。`~/.storiff/config.json` に `{"quiz": true}` があるときだけ作る。有効なら prep が「理解度クイズ: 有効」と1行出すので、それを見て判断する。

有効なときは、ステップごとに quiz を1問つける。読み飛ばしを止める関門になり、他人に説明できるところまで理解が届いたかを本人が確かめられる。

```json
"quiz": {
  "question": "この差分の後、`getUser(null)` を呼ぶと何が起きますか",
  "choices": ["例外が投げられる", "null がそのまま返る", "db.find が null で呼ばれる", "空のオブジェクトが返る"],
  "answer": 1,
  "explanation": "先頭に null を弾く分岐を足したので、db に届く前に例外になります"
}
```

- choices は4つくらい。answer は正解の番号で1始まり。explanation は1文か2文
- 差分の中身をたどらないと答えられない問いにする。ここが一番大事
- まちがいの選択肢ももっともらしくする。明らかに変な選択肢を混ぜると当てずっぽうで通ってしまう

良い問い

| 問い | なぜ良いか |
| --- | --- |
| この変更を入れる前は、`id` が null のとき何が起きていましたか | 変更前と変更後を見比べないと答えられない |
| このステップで足した早い return を消すと、どの処理が壊れますか | 差分の周りのコードまで読まないと分からない |
| 同じことは `map` でも書けるのに `forEach` にしたのはなぜですか | 書き方を選んだ理由まで考えさせる |

悪い問い

| 問い | なぜ悪いか |
| --- | --- |
| このステップでは何をしましたか | narration をそのまま読めば答えられる |
| 追加された関数の名前はどれですか | 差分を眺めて探すだけで、理解が要らない |
| 変更した行は何行ですか | 数えるだけで、中身と関わりがない |

quiz は任意なので、無くても画面は今まで通り動く。作りがおかしいときは check が ng にして理由を出す

## サブエージェントに渡す prompt

ステップ3では、下の文を本物の内容に置きかえて Agent tool(subagent_type: general-purpose)で呼び出す。`<dir>` は本物のパスにする。「作業メモ」は、この会話で実装していたなら要点を書き、していなければ行ごと消す。quiz の行は、prep が「理解度クイズ: 有効」と出したときだけ残し、出ていなければ行ごと消す

> steps.json を `<dir>/steps.json` に作り、`node ${CLAUDE_PLUGIN_ROOT}/storiff.js check <dir>` を実行して ng が出なくなるまで直してください。どのステップにも入らなかった変更IDは check が「補足」ステップに入れて埋めるので、全部を自分で数え上げる必要はありません。ステップの分け方は `${CLAUDE_PLUGIN_ROOT}/docs/story-schema.md` の「ステップの分け方」に従います。
>
> - まず `<dir>/context.txt`(意図の材料)を読む。ブランチ名、その差分に入っているコミットの本文、課題番号、`--with-remote` を付けたときは PR の説明とコメント、近くにある説明ファイルの場所が入っている。中身が薄いことも空のこともある
> - 次に `<dir>/files.txt`(ファイル一覧)で全体をつかみ、`<dir>/changes.txt`(変えた行だけ)で中身を読む。changes.json は開かない
> - `<dir>/hints.txt`(変更どうしのつながり)も読む。ここで定義した名前をあそこで使っている、という関係が並んでいる。関係の近いものを同じステップか隣のステップに置くと読み手が追いやすい
> - ただしヒントは参考であって命令ではない。名前の見た目だけで拾ったもので意図は見ていないので、外れも混ざるし、対応していない言語では空になる。ヒントのかたまりをそのままステップにしない。意図が違うなら関係が近くても分け、意図が同じなら関係が無くてもまとめる
> - owns は、ファイルまるごとなら F番号(例 `"F12"`)、一部なら変更IDの範囲(例 `"53-90"`)で書く。長いファイルパスは書かない
> - ステップを並べた順が画面の表示順になる。作った順に並べる
> - 1ステップは変えた行で数十行がまとまり。大きな変更をまとめすぎない。長いファイルは処理のまとまりで変更IDの範囲に分ける。広く薄い機械的な変更は1ステップでいい
> - 各ステップに title(見出し)と narration(説明文)を付ける。narration は日本語で、`code` や改行、行頭の - の箇条書きが使える
> - narration は「何をしたか」で止めず、「なぜ必要だったか(何に困っていたか)」と「他にどんなやり方があり、なぜそれを選ばなかったか」まで書く。コミットのメッセージには狙いしか書かれていないことが多く、困りごとと選ばなかった案は context.txt の課題や PR のコメントに落ちている
> - ただし context.txt にもコードにも無いことは書かない。材料が無いステップでは背景を作らず、コードから読み取れることだけを書く。根拠があるときは「コミットに〜と書いてある」のように出どころを添え、自分の読みで補ったところは読みだとわかるように書く
> - steps と同じ階層(steps.json の直下)に overview(全体像)を置く。`summary`(差分全体の要約)と `key_changes`(主な変更の箇条書き)と `risks`(気をつける点の箇条書き)。読み手がステップに入る前に全体をつかむためのもので、書き方は `${CLAUDE_PLUGIN_ROOT}/docs/story-schema.md` の「全体像」に従う。ステップの見出しの写しにしない
> - 各ステップに quiz(理解度クイズ)を1問つける。書き方と、良い問い悪い問いの見分け方は `${CLAUDE_PLUGIN_ROOT}/docs/story-schema.md` の「理解度クイズ」に従う。narration を読むだけで答えられる問いになったら作り直す
> - 呼び出しの順番や状態のうつり変わりが追いにくいステップにだけ `diagram` を付ける。名前の置きかえや設定の変更には付けない
> - 図は `flowchart LR` か `flowchart TD` で書き出し、そのステップが触るものだけを 8 ノードまでで書く。全体の構成図にはしない
> - 使えるのは `名前[ラベル]` と `名前(ラベル)` と `名前{ラベル}` と `A --> B` と `A -->|ラベル| B` だけ。名前は英数字にして日本語はラベルに書く。`subgraph` と `style` と `graph` の書き出しと `->` の矢印は使えない
> - 同じ名前に違うラベルを付けない。違う名前に同じラベルを付けない
> - 同じ変更IDを2つのステップの owns に入れない。再掲は refs にする。入れ忘れは check が「補足」ステップに埋めるので、拾いきれない変更IDが少し残っても直しにいかない。ただし全変更IDの半分以上は owns で覆う
> - 作業メモ(どんな順番で何のために作ったか): <この会話で実装した内容の要点。なければこの行を消す>
> - 終わったらステップの数と check の結果だけ返す
